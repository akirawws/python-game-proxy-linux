# Правила работы с Git

Документ фиксирует модель ветвления и требования к коммитам для проекта NetShield.

## Ветки

| Ветка | Назначение | Правила |
|---|---|---|
| `main` | Стабильная версия проекта | Прямые коммиты запрещены, только merge через pull request |
| `dev-<имя>` | Личная интеграционная ветка участника | Например, `dev-artur`, `dev-denis`, `dev-kirill` |
| `feature/<id>-<кратко>` | Новая функциональность | Ответвляется от `dev-<имя>`, вливается обратно в неё |
| `fix/<id>-<кратко>` | Исправление ошибки | Ответвляется от `dev-<имя>` или `main` при hotfix |
| `docs/<тема>` | Документация | Вливается в `dev-<имя>` |
| `test/<тема>` | Тесты и испытания | Вливается в `dev-<имя>` |

`<id>` — номер задачи из плана проекта, например `1.3` или `Ч1-37`.

Примеры имён:

```text
feature/1.3-configure-network
feature/1.2-lab-stand
fix/2.8-conntrack-counters
docs/git-workflow
```

## Жизненный цикл изменения

```bash
git switch dev-<имя>
git pull --ff-only origin dev-<имя>
git switch -c feature/1.3-configure-network

# ... изменения ...

git add <файлы>
git commit -m "feat(network): add interface checks and NAT setup"
git push -u origin feature/1.3-configure-network
```

Далее создаётся pull request в `dev-<имя>`. После проверки и merge ветка удаляется.
Периодически `dev-<имя>` синхронизируется с `main`, чтобы конфликты не накапливались.

## Коммиты

Используется формат Conventional Commits:

```text
<тип>(<область>): <краткое описание в повелительном наклонении>
```

Типы:

- `feat` — новая функциональность;
- `fix` — исправление;
- `docs` — документация;
- `test` — тесты;
- `refactor` — изменение структуры без изменения поведения;
- `chore` — инфраструктура, зависимости, конфигурация;
- `perf` — производительность;
- `ci` — CI/CD.

Области: `collector`, `detector`, `firewall`, `storage`, `api`, `web`, `security`, `network`,
`lab`, `docs`, `deploy`, `tests`.

Требования:

- заголовок не длиннее 72 символов;
- один коммит — одно логически завершённое изменение;
- в описании можно указать номер задачи: `Refs: 1.3`;
- не коммитить секреты, `.env`, базы данных, логи и временные файлы.

## Pull request

Перед созданием PR:

1. Прогнать релевантные тесты (`python -m pytest ...`).
2. Проверить, что в diff нет отладочных файлов и секретов.
3. Обновить документацию, если изменилось поведение или команды запуска.
4. Убедиться, что PR решает одну задачу и содержит ссылку на неё.

PR должен быть проверен хотя бы одним другим участником. В `main` попадают только изменения,
которые не ломают сборку и проходят согласованные проверки.

## Line endings

Правила зафиксированы в `.gitattributes`: все текстовые файлы хранятся с LF, Windows-скрипты —
с CRLF. Shell-скрипты нельзя переводить в CRLF: это ломает shebang при запуске на Linux.

## Теги и релизы

Итоговые версии отмечаются аннотированными тегами:

```bash
git tag -a v0.1.0 -m "NetShield: лабораторный стенд и базовая сеть"
git push origin v0.1.0
```

Тег ставится на коммит в `main` после приёмки соответствующего этапа.
