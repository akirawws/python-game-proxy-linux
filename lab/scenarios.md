# Сценарии лабораторных испытаний NetShield

Сценарии проверяют функциональность шлюза, обнаружение аномалий, автоматическую фильтрацию и безопасность. Испытания проводятся на собственном изолированном стенде (см. `lab/topology.md`).

## Общие правила

- Каждый сценарий задаёт: длительность, профиль нагрузки, целевой IP/порт, протокол, ожидаемое поведение, критерии прохождения.
- Конкретные скорости нагрузки выбираются по результатам измерения производительности стенда.
- Нагрузочные проверки не затрагивают чужие сети и публичные серверы.

## Функциональные сценарии (T01–T12)

| ID | Сценарий | Ожидаемый результат |
|----|----------|---------------------|
| T01 | Пересылка TCP | Разрешённое TCP-соединение проходит через шлюз |
| T02 | Пересылка UDP | Разрешённые UDP-пакеты достигают тестового сервера |
| T03 | Несколько портов | Каждый порт обрабатывается согласно своей политике |
| T04 | Несколько серверов | Правила одного сервера не влияют на остальные |
| T05 | Запрещённый порт | Пакеты к запрещённому порту блокируются |
| T06 | Обход шлюза | Прямой доступ к backend извне невозможен (в предусмотренной топологии) |
| T07 | NAT и обратный маршрут | Ответы доходят до клиента, соединения работают в обоих направлениях |
| T08 | Перезапуск шлюза | Настроенные постоянные правила восстанавливаются |
| T09 | Перезапуск Python | Базовая фильтрация продолжает работать |
| T10 | Ошибка конфигурации | Некорректные правила отклоняются без нарушения текущей политики |
| T11 | Проверка Web-панели | Доступные страницы отображают актуальные данные |
| T12 | Проверка авторизации | Неавторизованный пользователь не может управлять защитой |

## Сценарии обнаружения аномалий (A01–A12)

| ID | Сценарий | Ожидаемое поведение |
|----|----------|---------------------|
| A01 | Обычная низкая нагрузка | Аномалия не регистрируется |
| A02 | Постепенный рост TCP-соединений | Detector фиксирует превышение порога |
| A03 | Резкий всплеск новых TCP-соединений | Событие с указанием причины |
| A04 | Резкий рост UDP PPS | Событие при выполнении условий обнаружения |
| A05 | Необычная активность одного источника | Источник выявляется (если есть метрики по IP) |
| A06 | Резкое увеличение числа источников | Фиксируется изменение распределения источников |
| A07 | Высокий трафик без высокой частоты соединений | Аномалия по байтам или PPS (если настроены пороги) |
| A08 | Кратковременный легитимный пик | Нет автоматической постоянной блокировки |
| A09 | Длительное превышение нормы | Событие сохраняется, применяется действие |
| A10 | Снижение нагрузки | Временные ограничения снимаются по политике |
| A11 | Недоступность источника метрик | Ошибка сбора, а не ложный вывод об отсутствии трафика |
| A12 | Перезапуск Detector | Базовая защита сохраняется, анализ восстанавливается |

## Испытания автоматической фильтрации

Для каждого сценария, где Detector обнаружил аномалию, проверяется:

1. Создалось ли событие.
2. Указана ли причина срабатывания.
3. Выбрано ли разрешённое действие.
4. Применилось ли правило nftables.
5. Повлияло ли правило только на целевой сервис или источник.
6. Записались ли время применения и срок действия.
7. Снялось ли временное правило после истечения срока.
8. Продолжили ли работать легитимные подключения.
9. Сохранилась ли защита после перезапуска Python.
10. Записалась ли ошибка, если применение правила завершилось неудачно.

Дополнительно проверяется режим наблюдения: обнаружение работает, но правила автоматически не применяются.

## Испытания скриптов безопасности Linux

- Повторный запуск каждого скрипта.
- Запуск без root-привилегий там, где это допустимо.
- Обработка отсутствующих пакетов и интерфейсов.
- Проверка синтаксиса до применения конфигурации.
- Проверка резервного копирования и восстановления.
- Попытка доступа к административной панели извне разрешённой сети.
- Проверка открытых портов.
- Проверка SSH-доступа после применения настроек.
- Восстановление работы после неудачного изменения конфигурации.

## Проверка безопасности веб-приложения

- Неверный пароль и многократные попытки входа.
- Запросы к API без авторизации.
- Истёкшая сессия.
- CSRF (если используются cookie-сессии).
- Попытка передать некорректный IP, порт или протокол.
- Попытка добавить запрещённое правило.
- Попытка передать shell-команду вместо параметров действия.
- Отсутствие паролей и секретов в журнале.
- Ограничение доступа к конфигурационным файлам и базе данных.

## Критерии успеха

| Показатель | Предварительный критерий |
|------------|--------------------------|
| Корректность маршрутизации | Все тесты TCP/UDP проходят |
| Изоляция правил | Изменение одного сервера не затрагивает остальные |
| Работа фильтрации | Все тесты разрешения и блокировки проходят |
| Обнаружение аномалий | Recall не менее 90% на отложенном наборе тестов |
| Ложные срабатывания | Не более 5% на наборе легитимных интервалов |
| Время обнаружения | Не более 5 секунд |
| Время применения правила | Не более 2 секунд после решения Detector |
| Задержка | p95 не более 5 мс в лабораторном профиле |
| Работа при отказе Python | Базовая фильтрация сохраняется |
| Автоматическое снятие правил | Временные правила снимаются по сроку |
| Аутентификация | Все тесты неавторизованного доступа проходят |
| Журналирование | Все применения и ошибки правил фиксируются |
| Восстановление | Конфигурация восстанавливается из резервной копии |
